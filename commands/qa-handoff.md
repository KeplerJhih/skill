# Command: /qa-handoff（測試交接）

> **📍 全域唯一正本**：本檔位於 `~/.claude/commands/qa-handoff.md`，對所有專案生效；各專案**不得**放拷貝。
> 內容**不得寫死專案名詞**（專案名、路徑、裝置型號、功能開關、測試帳號）——專案特定前置一律從該專案 CLAUDE.md / docs 讀取，讀不到就留 `TODO(owner)`。

## 用途與時機

開發 session 代碼寫完、**單元測試與編譯已通過**之後呼叫。用戶會另開一個 session（通常是不同模型）執行 E2E；本 command **只做交付端**，產出兩樣東西：

1. `docs/<tag>-test-plan.md` — 測項 + QA 規則 + 交付規格，是 QA 端的**單一真相來源**
2. 一段**可直接複製到新對話**的 QA 提示詞（貼在完成回報末尾）

QA session 不需要任何 command；規則全在計畫檔，提示詞只負責啟動與指向。
測完後 QA 會回傳一段提示詞，用戶貼回開發 session，開發 session 以 `/doit` 讀 fix-brief 逐條修。

**引數**：`$ARGUMENTS`（可選 `tag`；未給時取子專案版本號 — Xcode `MARKETING_VERSION` / `package.json` version / `VERSION` 檔 — 取不到就用功能 slug）

---

## 🛑 閘門（輸出任何文字前，順序不可省）

1. 以 Skill 工具載入名稱含 `karpathy-guidelines` 的 skill（以當前清單實際名稱呼叫）。
2. `Read` 根 `CLAUDE.md` 與本次變更所在子專案的 `CLAUDE.md`（`~/.claude/shared/workflow-base.md`「專案偵測」步驟 0）。
3. 依平台載入對應 skill（iOS → native-ios；web → frontend / qa；backend → 對應 backend skill）。目的是知道該平台的**驗證工具與已知踩坑**，不是要重做開發。

## 執行步驟

### Step 1：收斂變更範圍

- 來源：本次對話的藍圖與完成回報、`git status --short`、`git diff --stat`（對分支 base）。
- 整理成兩欄：
  - **開發端已驗**：單元測試（指令 + 結果）、編譯、已做過的 E2E —— 寫進計畫檔，讓 QA 不重跑
  - **交 QA**：只能靠操作 UI / 打 API / 真機才能驗的行為
- 分支與 commit 狀態要在計畫檔明講（例：「分支 X，變更未 commit」）。

### Step 2：偵測驗證環境

| 平台 | 部署 / 操作工具 | 註 |
|------|----------------|----|
| iOS | xcodebuildmcp（build_run_sim）+ ios-simulator（截圖 / tap / type）；MCP 不可用時 `xcodebuild` + `xcrun simctl` | 模擬器對動畫、系統玻璃元件、拖曳門檻、HID 打字（IME）不可信 → 這些列「真機限定」或「不算 bug 的限制」 |
| web | chrome-devtools MCP（qa skill） | 需先起 dev server；啟動指令寫進前置 |
| backend | curl / 專案測試指令 | 契約檔路徑一併給 |

- **專案前置**（測試帳號、付費牆或 feature flag 開關、假資料、模擬器鍵盤設定、必要 env）：從子專案 CLAUDE.md、docs、`.env.example` 找；找不到就在計畫「前置」段留 `TODO(owner)` 請用戶補，**不要猜**。
- 專案 `docs/` 若已有前一版的 test-plan / test-report / fix-brief，格式對齊它（欄位、編號、嚴重度定義沿用）。

### Step 3：寫 `docs/<tag>-test-plan.md`

落點：變更所在子專案的 `docs/`（沒有就建立）。骨架如下；功能段落依變更性質增減，**「QA 規則」「問題回報格式」「測完交付」三段必有**。

~~~markdown
# <tag> 測試計畫（人工 / 測試 session 用）

分支 `<x>`（變更<已 / 未> commit）。範圍：<一段話>。
開發端已驗：<單元測試指令與結果、編譯、已做的 E2E>，QA 不必重跑。
設計文件：<路徑>。

## 0. 前置
- 環境 / 部署指令 / 假資料或測試帳號 / 開關設定（讀不到的寫 TODO(owner)）
- 已知**不算 bug** 的環境限制清單（模擬器渲染、IME、拖曳門檻、第三方站台行為…）

## A. <主線功能>（主測）
| # | 步驟 | 預期 |
|---|------|------|
（預期必須是可觀察的數字 / 文案 / 狀態；有「多處一致」核對點時逐處列出）

## B. <邊界與反向操作>（超額、歸零、刪除後回復、結清後再動…）
## C. <對照組>（同語意的既有功能，驗兩邊行為與文案一致）
## D. 舊資料相容（動到資料模型 / 持久層 / 遷移時必有：既有資料頁面零變化、匯出入 round-trip、殺 app 重開、跨裝置同步）
## E. 迴歸抽查（被改動路徑的相鄰功能）
## F. 語系 / 視覺 / 真機限定

## QA 規則
- 不修改任何源碼；發現 bug 只記錄。
- 測試階段黑箱（操 UI / 打 API / 看 console、network）；**寫工單階段可讀源碼定位**，但根因一律標「假設」。
- 工具或環境壞了停手回報用戶，不繞道、不自行改 server / 資料狀態。
- 「前置」列出的限制不算 bug，標註為限制；無法穩定重現的記「偶發」並附觀察到的操作序列。
- crash、算錯數據（金額 / 數量 / 統計）一律 P0，附 console 訊息。

## 問題回報格式（寫進 docs/<tag>-test-report.md）
一條一個問題，照下面格式追加；步驟要能重現、實際行為要具體。截圖放 `docs/<tag>-test-shots/`。

```markdown
### [P1] 短標題（一句話講清哪裡壞）
- 測項:B2（對應上表編號;清單外的寫 NEW）
- 環境:<模擬器型號 / OS 版本 或 真機型號 / OS 版本>
- 步驟:
  1. ...
- 預期:...
- 實際:...（錯誤文字照抄;視覺問題附截圖檔名）
- 頻率:必現 / 偶發(約 N 次中 1 次)
```

嚴重度:**P0** crash / 資料錯誤・**P1** 功能不可用・**P2** 視覺 / 文案。不確定標 P1。同一問題不重複開條。

## 測完交付（整理成開發可複查的形式）
1. `docs/<tag>-test-report.md`：全部測項 PASS / FAIL / SKIP 總表 + 問題條目（每個 FAIL 必附可重現步驟與截圖）。
2. `docs/<tag>-fix-brief.md`：每條 F# 含 症狀 / 位置（檔案:行）/ 根因假設 / 修法建議 / 嚴重度 / 是否本次新增；開頭給修復順序建議。
3. 「建議開發親自看」清單（有必要時）：真機限定、偶發、無法判定是否為 bug 的項目。
4. 對話結尾貼一段給開發 session 的提示詞：一句總結（幾項 PASS / FAIL / SKIP）+ 指向上述檔案 + 修復順序 + 「用 /doit 讀 fix-brief 逐條修」。
~~~

### Step 4：測項設計原則（寫計畫時的自我約束）

1. **先主線後邊界**：A 段是使用者最常走的路，先確保它對。
2. **多處一致**：同一個數字出現在幾個畫面就列幾個核對點（列表 / 明細 / 總覽 / 報表 / 匯出）。
3. **相容性**：動到資料模型就要有「既有資料頁面零變化」+ round-trip（匯出入 / 重啟 / 同步）。
4. **對照組**：找同語意的既有功能，驗兩邊行為與文案一致，順便抓出反向對齊債。
5. **份量**：每段 ≤ 8 項，總量控制在一個 session 跑得完（約 30–45 項）；超過就砍非主線。
6. **可觀察**：預期寫數字、文案、狀態，不寫「正常」「合理」。
7. **不重列**：單元測試已覆蓋的純計算不列 E2E，只列它在 UI 上的呈現。

### Step 5：產出 QA 提示詞

貼在完成回報**末尾**，用 code block 包起來讓用戶一鍵複製。固定模板（`<>` 換成本次內容；**不重抄計畫檔內容，只指向**）：

```
你是 <專案> 的 QA 測試 session，對 <分支 / tag> 做 <平台> E2E 測試，不修改任何程式碼。

背景
- Repo：<子專案路徑>（分支 <x>，變更<已 / 未> commit）。先讀 <子專案 CLAUDE.md>、<設計文件>、<docs/<tag>-test-plan.md>。
- 本次功能：<兩三行>。
- 開發端已驗：<單元測試指令與結果、編譯>，不必重跑。

任務
1. 依 docs/<tag>-test-plan.md 逐項執行；用 <部署 / 操作工具> 部署與操作；每項記 PASS / FAIL / SKIP。
2. <本次最重要的核對點，一到兩句>。

規則
依計畫檔「QA 規則」段：不改源碼、工具壞了停手回報、前置列的限制不算 bug、crash 與數據錯誤一律 P0。

交付（測完在對話結尾）
- 依計畫檔「測完交付」段，把結果整理成開發可複查的形式：docs/<tag>-test-report.md（總表 + 可重現的 FAIL 條目 + 截圖）、docs/<tag>-fix-brief.md（含位置與根因假設、修復順序）。
- 有必要時列「建議開發親自看」清單（真機限定、偶發、無法判定的項目）。
- 最後貼一段給開發 session 的提示詞（一句總結、檔案路徑、修復順序），我會直接複製回去。
```

### Step 6：完成回報

- 計畫檔路徑、段落與測項數
- 開發端已驗清單、留給用戶補的 `TODO(owner)`
- 提示詞 code block（放最後一段）

## 禁止事項

- ❌ 在 command 或提示詞裡寫死專案專屬前置（應從專案 CLAUDE.md / docs 讀）
- ❌ 把單元測試已覆蓋的純計算再列成 E2E 測項
- ❌ 幫 QA 預設結論（「這項應該會過」）
- ❌ 提示詞重抄計畫檔內容 — 只指向
- ❌ 幫 QA 端另設 command 或流程 — QA 只需要提示詞 + 計畫檔
