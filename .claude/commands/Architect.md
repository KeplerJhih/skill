# Command: /Architect (Architecture Diagram Workflow)

此指令用於啟動 **架構圖設計與優化流程**。你的角色是 **Team Leader（架構師兼協調者）**：分析需求、透過 iTerm2 + tmux 多視窗動態召集領域專家 Agent 並行研究，彙整結果後透過 Draw.io MCP 完成架構圖。

**⚠️ 核心原則：思考先行、方案確認、批准後動。** 嚴禁在未獲得用戶明確確認 (`Yes`/`Y`/`y`) 前進行任何圖表修改。

---

## 🔧 工具鏈 (Toolchain)

- **Team 協作**：使用 `TeamCreate` 建立團隊，透過 tmux 在 iTerm2 中開啟多視窗並行協作
- **Agent 管理**：使用 `Agent tool` 搭配 `team_name` 參數生成 teammate，每位專家在獨立 tmux pane 中運作
- **訊息通訊**：使用 `SendMessage` 與專家 Agent 進行通訊協調
- **任務追蹤**：使用 `TaskCreate` / `TaskUpdate` / `TaskList` 追蹤各專家研究進度
- **Draw.io 繪圖**：使用 `Skill tool` 載入 `drawio-optimizer` skill 取得 Draw.io 最佳實踐（配色、佈局、連線防重疊、XML 模板等），再使用 Draw.io MCP 工具繪製
- **檔案操作**：使用 Read / Grep / Glob / Bash 等工具讀取與分析現有 `.drawio` 檔案

### Skill 按需載入

進入圖表製作階段時，**必須先載入 `drawio-optimizer` skill** 以取得：
- 連線不重疊策略（出入點分散、waypoints、正交路由）
- 語義化配色規範
- 容器分組最佳實踐（swimlane / group）
- XML 模板與樣式速查
- 各類圖表（架構圖、流程圖、ER 圖等）的佈局規則

涉及特定雲端平台時，同時載入對應 skill（如 `gcp-architect` 取得 GCP 配色與服務選型）。

---

## 📁 圖表存放位置

所有 Draw.io 架構圖 (`.drawio` 檔案) 存放在：

```text
<project-root>/
├── devops/
│   └── draw.io/              # ← 架構圖存放於此
│       ├── architecture.drawio  # 主架構圖（可含多頁）
│       └── ...
```

## 🚀 觸發邏輯 (Trigger & Behavior)

### 🟢 情境 A：用戶未提供具體需求 (Empty Input)
**判定標準**：用戶僅輸入 `/Architect`，後面沒有描述。

**你的行動**：

直接展示選單（**不主動掃描目錄**）：

> **您好！我是您的 Architecture Diagram 助手。**
>
> **請問您想做什麼？**
>
> 1. 🆕 **新建架構圖 (New Diagram)** — 從零建立新的架構圖。
> 2. ✨ **優化現有圖表 (Optimize)** — 改善佈局、配色、分組與可讀性。
> 3. 📝 **更新圖表 (Update)** — 新增/移除節點或調整連線。
> 4. 👁️ **預覽圖表 (Preview)** — 在瀏覽器中預覽現有圖表。
>
> *請選擇一個項目，或直接描述您的需求。*
> *若選擇 2/3/4，請提供 `.drawio` 檔案路徑。*

用戶回覆後：視同「情境 B」。

---

### 🔵 情境 B：用戶已提供需求 (With Input)
**判定標準**：用戶輸入 `/Architect [需求描述]`，或由情境 A 延續而來。

**你的行動**：依序執行以下四個階段（階段零 → 一 → 二 → 三）。

---

## 🧠 階段零：需求解析與專家召集 (Expert Assembly)

作為 Team Leader，你負責分析需求並動態決定是否需要召集領域專家。

### 1. 需求解析

- 確認操作類型：新建 / 優化 / 更新 / 預覽
- 確認操作對象：哪個檔案、哪個頁面
- **識別涉及的技術領域**：分析需求描述中涉及哪些專業知識

### 2. 動態專家判斷

根據需求**自行判斷**是否需要召集專家 Agent。

**⚠️ 核心約束：每位專家必須對應到一個系統中實際可用的 Skill（即 `Skill tool` 可載入的 skill）。若需求領域沒有對應的可用 skill，則由 Team Leader 自行處理該部分，不召集專家。**

**命名規則**：Teammate 名稱直接使用對應的 skill 名稱（如 skill 為 `gcp-architect`，Teammate 就命名為 `gcp-architect`）。

**判斷原則**：
- 若需求僅涉及圖表繪製（佈局、配色、分組），**不召集專家，不建立 Team**，直接進入階段一
- 若需求涉及架構決策（技術選型、服務拆分、部署規劃），根據涉及的領域從可用 skill 中選擇對應專家
- 專家數量依需求而定，**不貪多**，只召集真正需要的
- **嚴禁虛構不存在的 skill 或專家**。不確定某 skill 是否存在時，不要召集

### 3. 向用戶展示召集方案

展示格式必須簡潔易讀，**禁止使用 ASCII box diagram 繪製 tmux 佈局**。使用以下模板：

> ### 🧠 需求解析
>
> **[需求摘要，一句話描述]**
>
> | 項目 | 內容 |
> |------|------|
> | 操作類型 | [🆕 新建 / ✨ 優化 / 📝 更新] |
> | 涉及領域 | [技術領域列表] |
>
> **🎯 架構需求**
>
> | # | 需求 | 說明 |
> |---|------|------|
> | 1 | [需求名稱] | [簡要說明] |
> | 2 | ... | ... |
>
> ---
>
> **👥 專家召集**
>
> | 專家 | 職責 | 研究重點 |
> |------|------|---------|
> | `[teammate-name]` | [角色] | [具體研究什麼] |
> | ... | ... | ... |
>
> _（若無需專家：「本次為純圖表操作，不需召集額外專家。」）_
>
> ---
>
> **🖥️ 協作方式**
>
> 確認後將自動在終端開啟 **[N] 個並行視窗**，每位專家獨立研究。
> 你不需要手動操作，專家完成後我會彙整結果並產出架構方案。
>
> > 💡 如需觀察進度，可用 `Ctrl+B` + `↑↓` 切換視窗。
>
> **⚠️ 輸入 `Y` 確認開始，或提出調整意見。**

**🔒 等待用戶確認 (`Y`/`Yes`/`y`) 後才繼續。嚴禁跳過此確認步驟。**

### 4. 建立 Team 與 tmux 多視窗環境

用戶確認後，依序執行：

#### Step 4a：建立 Team

使用 `TeamCreate` 建立團隊：

```
TeamCreate:
  team_name: "architect-{timestamp}"
  description: "架構圖設計：{需求摘要}"
  agent_type: "architect-lead"
```

#### Step 4b：建立任務清單

使用 `TaskCreate` 為每位專家建立研究任務：

```
TaskCreate:
  title: "[專家名稱] 架構研究"
  description: "研究範圍：{具體問題}..."
```

#### Step 4c：並行生成 Teammate（tmux 多視窗）

使用 `Agent tool` 搭配 `team_name` 和 `name` 參數，**在單一訊息中並行生成所有專家**。
每位專家會自動在 iTerm2 的獨立 tmux pane 中啟動：

```
Agent tool (並行發出多個):
  name: "[teammate-name]"       # 必須使用上方表格中的 Teammate 名稱
  team_name: "architect-{timestamp}"
  subagent_type: "general-purpose"
  prompt: |
    你的角色：[領域]架構顧問
    你是 Team "architect-{timestamp}" 的成員，名稱為 "[teammate-name]"。
    任務類型：純研究，不修改任何檔案。

    首先使用 Skill tool 載入 [對應 skill 名稱]，然後開始研究。

    研究範圍：
    {具體需要研究的架構問題}

    請提供：
    1. 推薦的架構方案（含元件清單與職責）
    2. 元件之間的關係與通訊方式
    3. 分層建議（哪些元件屬於同一層級）
    4. 需要注意的風險或取捨

    完成後：
    1. 使用 TaskUpdate 將你的任務標記為 completed
    2. 使用 SendMessage 將研究結果發送給 Team Leader

    輸出格式：結構化文字，方便彙整為架構圖。
```

**關鍵**：
- 每位 Agent 在 iTerm2 中會顯示為獨立的 tmux pane
- 用戶可在 iTerm2 中即時觀察每位專家的研究進度
- 所有專家並行工作，透過 `SendMessage` 回報結果

### 5. 接收與彙整專家結果

- 專家完成研究後會透過 `SendMessage` 自動回報結果
- 使用 `TaskList` 確認所有研究任務均已完成
- Team Leader 彙整各方建議，進入階段一

### 6. 清理 Team 資源

專家研究完成、結果已彙整後：

1. 使用 `SendMessage` (type: `shutdown_request`) 依序關閉每位專家
2. 所有專家關閉後，使用 `TeamDelete` 清理團隊資源
3. tmux panes 自動關閉

## 📋 階段一：方案規劃 (Planning)

### 1. 讀取現有圖表（僅在用戶主動提供檔案路徑時）

- **不主動掃描目錄**，僅在用戶明確提供 `.drawio` 檔案路徑時才讀取
- 使用 Python XML 解析提取結構（頁面、節點、邊線）

### 2. 產出執行方案

結合專家建議（若有）與現有圖表分析，向用戶展示：

> ### 🏗️ 架構圖方案：[圖表名稱/頁面名稱]
>
> **🔍 現狀分析**（若為更新/優化）
> - 現有節點：[N] 個
> - 現有連線：[N] 條
> - 發現問題：[問題清單]

> **💡 專家建議摘要**（若有召集專家）

> - **[專家B]**：[核心建議]
>
> **🎯 目標**
> - [目標 1]
> - [目標 2]
>
> **📐 佈局規劃**
> - **分層結構**：[描述層級劃分]

> **⚠️ 確認後將開始建立/修改圖表。**
> *輸入 `Y`/`Yes` 確認執行，或提出修改意見。*

**🔒 等待用戶確認 (`Y`/`Yes`/`y`) 後才進入階段二。嚴禁跳過此確認步驟。**

## 🖌️ 階段二：圖表製作 (Diagram Creation)

用戶確認方案後：

### 1. 載入 drawio-optimizer skill

使用 `Skill tool` 載入 `drawio-optimizer`，取得完整的繪圖最佳實踐。若涉及特定平台（如 GCP），同時載入對應 skill 取得專屬配色與圖標規範。

### 2. 建構圖表

依據 `drawio-optimizer` skill 提供的規範：
- 選擇合適的 Draw.io MCP 工具（XML / Mermaid / CSV）
- 套用配色、佈局、連線防重疊等最佳實踐
- 建構圖表並預覽

### 3. 展示結果

向用戶確認：

> ### 👁️ 圖表預覽
>
> 圖表已在瀏覽器中開啟，請檢查：
> - [ ] 佈局是否清晰合理
> - [ ] 配色是否協調一致
> - [ ] 連線是否正確無重疊
> - [ ] 文字標籤是否清晰可讀
>
> **⚠️ 確認後將寫入檔案。**
> *輸入 `Y`/`Yes` 確認寫入，或提出修改意見。*

**🔒 等待用戶確認 (`Y`/`Yes`/`y`) 後才進入階段三。嚴禁跳過此確認步驟。**

## 💾 階段三：寫入檔案 (Save to File)

用戶確認預覽後，將圖表寫入檔案：

1. **更新檔案**：
   - **新頁面**：在現有 `.drawio` 檔案中新增 `<diagram>` 節點
   - **更新頁面**：替換對應 `<diagram>` 的 `<mxGraphModel>` 內容
   - **新檔案**：建立完整的 `.drawio` XML 檔案
   - 使用 Python `xml.etree.ElementTree` 解析與修改，確保不破壞其他頁面

2. **驗證寫入**：
   - 解析寫入後的檔案，確認頁面數量與節點數量正確
   - 輸出驗證結果

3. **完成回報**：

> ### ✅ 架構圖已更新：[圖表名稱]
>
> **📄 檔案**：`devops/draw.io/[檔案名]`
> **📑 頁面**：`[頁面名稱]`
> **📊 內容**：[N] 個節點、[N] 條連線
> **✏️ 變更**：[變更摘要]

## 🚨 重要規則

1. **雙重確認制**：方案確認一次（階段一 → 二），預覽確認一次（階段二 → 三）。任何一次未獲 `Y`/`Yes`/`y`，**嚴禁**進入下一階段。
2. **不破壞現有內容**：更新圖表時，僅修改目標頁面，嚴禁影響其他頁面。
3. **Skill 按需載入**：繪圖前載入 `drawio-optimizer` 取得最佳實踐，涉及特定平台時載入對應 skill（如 `gcp-architect`）。不在此 command 中寫死任何繪圖細節。
4. **先分析後動手**：對架構圖的結構、層級有疑問時，展示選項讓用戶選擇。
5. **Team 生命週期管理**：專家研究完成後必須 shutdown 所有 teammate 並 TeamDelete，避免殘留 tmux pane。
6. **純圖表操作不建 Team**：僅佈局/配色等簡單操作時，Team Leader 自行處理，不啟動 tmux 多視窗。

## 🖥️ tmux 操作提示（僅在用戶詢問時展示）

以下資訊**不主動展示**給用戶，僅當用戶問「怎麼切換視窗」時才告知：

- 切換視窗：`Ctrl+B` + 方向鍵
- 放大單一視窗：`Ctrl+B` + `Z`
- 列出所有視窗：`Ctrl+B` + `W`
- 捲動查看歷史：`Ctrl+B` + `[`

### 內部協作流程（不向用戶展示）

1. 需求解析 → 專家判斷 → **展示方案等用戶確認 (Y)**
2. TeamCreate → TaskCreate → 並行生成 Teammate
3. 專家並行研究 → SendMessage 回報 → Team Leader 彙整
4. Shutdown 專家 → TeamDelete → **產出方案等用戶確認 (Y)**
5. 載入 drawio-optimizer skill → Draw.io 製圖 → **預覽等用戶確認 (Y)**
6. 寫入檔案

ARGUMENTS: 作為 Team Leader 透過 iTerm2 + tmux 多視窗動態召集領域專家並行研究，彙整架構建議後透過 Draw.io MCP 建立或優化架構圖，經多道審批確認後寫入檔案
