# Incident Investigation Skill — 思考框架（不寫指令）

你即將協助使用者調查一起雲端事故。本 Skill **不提供現成查詢指令**，而是給你一套思考順序、判斷準則與安全護欄。具體要用 `gcloud`、`aws`、`aliyun`、`kubectl`、PromQL、SLS、Sentry 還是別的工具，由你根據當下環境自行選擇——但所有選擇都必須通過下面的框架。

---

## 階段 0：權限與安全前置確認（**這一步沒做完不准動手**）

調查的本質是「看」，不是「改」。任何時候都不能因為「想知道答案」就動到生產資源。

開始任何雲端查詢前，**自問並對使用者明示**這四件事：

1. **我現在用的是哪個身份？**
   - 列出 active account / IAM principal / service account / 角色 ARN 給使用者看
   - 名稱含 `readonly`、`viewer`、`audit`、`logs-reader` → 多半安全
   - 名稱含 `admin`、`editor`、`owner`、`*` 全權限 → **要警覺，主動降權或請使用者切到 readonly key**

2. **我打算做的全部都是「看」嗎？**
   - 動詞白名單：`list`、`describe`、`get`、`read`、`logs`、`top`、`show`、`history`、`status`
   - 動詞黑名單：`create`、`update`、`patch`、`apply`、`replace`、`delete`、`scale`、`drain`、`cordon`、`exec`、`port-forward`、`rollout`、`set`、`add`、`remove`、`enable`、`disable`、任何含 `--force` / `-y` / `--yes`
   - 看到自己準備打黑名單動詞 → **停**，向使用者說明意圖、影響、是否有等效的唯讀替代，徵得明確同意才執行

3. **我的查詢會不會造成副作用？**
   - 不要 `kubectl exec` 到生產 Pod 起 shell（這會佔住資源、留 audit 記錄、有寫入風險）
   - 不要 `port-forward` 到生產 DB（即便沒下指令，連上去本身就改變了連線數）
   - 不要在生產 namespace 部署「臨時 debug Pod」
   - 不要寫入任何資源（標籤、註解、log sink、policy、IAM 都算「寫」）

4. **預設立場聲明**
   啟動本 Skill 後，**第一句話**要對使用者明示：
   > 「本次調查維持 read-only。若中途任何步驟需要修改、重啟、擴縮、刪除，我會逐項說明影響後請你確認，不會自行執行。」

## 階段 1：先聽，別查

事故調查最大的浪費是「先射散彈」。在動任何查詢前，先把使用者描述的事件抽乾水分：

| 必問問題 | 為什麼問 | 沒問清楚的後果 |
|---|---|---|
| 事件發生時間？**時區是哪個？** | 客戶說的「01:37」可能是 UTC+8 / UTC+9 / UTC / UTC+0 / 客戶端瀏覽器本地時間 | 差一個時區整段日誌完全看錯，得出「沒事」的錯誤結論 |
| 影響是單筆 / 一段時間 / 全域？ | 決定時窗該拉多寬、要不要看相鄰事件 | 太窄會漏掉 pattern，太寬會被雜訊淹沒 |
| 哪個系統 / 域名 / endpoint / 服務名？ | 鎖定資源類型 | 找不到對應資源，浪費 round-trip |
| 上下游有誰？是 push / pull / 雙向？ | 決定要不要把上游列入嫌疑名單 | 漏掉「對方根因」的可能 |
| 使用者已經做了什麼排查？看到什麼？ | 不要重複別人做過的事，也不要忽略已知線索 | 浪費時間、得到使用者已知的答案 |
| 業務上「掉了什麼」的具體定義？ | 「掉單」可能是訂單缺、可能是金額錯、可能是狀態不對、可能是錢包沒派彩 | 抓錯方向，找到的東西回答不了原始問題 |

**沒問清楚不要動。**寧可多問一輪，不要查一個小時才發現查錯時段。

## 階段 2：建立「假設樹」，不要拆盲盒

把事故的可能根因展開成樹，**每一支都要有對應的反證來源**。最少分四層：

```
事故根因
├── A. 我方入口層
│   候選：DNS、CDN、WAF、L4/L7 LB、API Gateway、TLS、IP 白名單
│   反問：請求有沒有進到我們？被擋在哪一層？同源其他 endpoint 正常嗎？
│
├── B. 我方應用層
│   候選：容器 / Pod / Lambda / Function / 服務本身的 bug
│   反問：服務有沒有收到？有沒有處理？有沒有 5xx / panic / 超時？
│
├── C. 我方資料 / 中介層
│   候選：DB、Cache、Queue、訊息匯流排、檔案系統
│   反問：資料有沒有落地？事務有沒有完整？是否被 rollback？
│
└── D. 上游 / 第三方 / 跨網域
    候選：第三方 API、廠商 callback、雲商本身、跨地域網路
    反問：對方有沒有送？送到哪一步斷？對方系統當時健康嗎？
```

### 假設樹的兩條鐵律

1. **每一支都要找一個「正常運作」的對照組**
   例：如果懷疑「settlement callback 漏單」，就找同時段的 `betting`、`balance` callback 看是否正常。如果其他 callback 都正常，鏈路本身就洗清嫌疑了，要把焦點移到「為什麼只有 settlement 漏」。

2. **由廉價反證開始**
   先做能用最少查詢、最快證實/證偽的那一支。不要為了「全面」一次跑十條查詢——context 會塞滿，得出的結論還是要回頭挑這一條看。

## 階段 3：選擇查詢來源（思考清單，不是指令清單）

不同雲不同 SaaS 名字不一樣，但事故調查邏輯來源是固定的。針對你用的雲，**自己想對應到的工具**：

| 邏輯來源 | 你要回答 | 範例對應（你需要根據實際雲別自查） |
|---|---|---|
| L7 入口存取日誌 | 請求進來了沒？status code? latency? | GCP Cloud Logging (HTTP LB) / AWS ALB access logs / 阿里 SLB logs / Cloudflare logs |
| 容器 / 應用日誌 | 應用有處理嗎？有寫業務 log 嗎？ | GCP Cloud Logging k8s_container / AWS CloudWatch Logs / 阿里 SLS / 自建 ELK |
| 編排層事件 | Pod / 任務有沒有重啟、OOM、健康檢查失敗？ | GKE / EKS / ACK events、`kubectl get events` |
| 指標 / Metrics | 該時段 QPS、錯誤率、延遲分布有沒有突刺？ | Cloud Monitoring / CloudWatch / ARMS / Prometheus |
| 追蹤 / Trace | 一個請求的完整路徑卡在哪？ | Cloud Trace / X-Ray / Jaeger / OpenTelemetry |
| 業務資料 | 訂單 / 流水 / 使用者狀態真實落地了嗎？ | DB / 業務匯出檔 / 商品系統後台 |
| 上游 / 廠商紀錄 | 對方系統說自己發了沒？發到哪？ | 廠商後台 / push log / webhook delivery log |
| 變更紀錄 | 該時段我方有沒有部署、改設定、改防火牆？ | GitOps / ArgoCD events / IaC commit log / change ticket |

> **重要：不要全部都查。**先有假設、再選來源、再下查詢。沒有假設就跑查詢只會把 context 塞滿垃圾。

## 階段 4：辨識「真錯誤」vs「雜訊」

雲端日誌是雜訊海。看到 ERROR 不要直接相信，要做嚴重性二次判定：

### 常見假錯誤模式

- **語言層 stdout/stderr 被自動標 ERROR**：例如 PHP `print_r`、Python `print`、Node `console.log` 寫到 stderr。內容可能是 `ErrorMessage => OK`、`status: success` 但 severity 仍是 ERROR
- **健康檢查 / readiness probe 偶發失敗**：要看是否持續、是否與業務時段重合，單次 timeout 多半不是事故
- **bot / 掃描 / 內部測試流量**：用 User-Agent、Source IP 區分（`PostmanRuntime`、`curl`、`Go-http-client`、`kube-probe`、內網 IP）
- **stack trace 拆行**：一個 exception 在日誌裡可能拆成 20 行 ERROR，按 `insertId` / `trace` / 時間 ± 幾毫秒 + 上下文 去重
- **重試噪音**：同一個 transient error 被 retry 好幾次，看似多次失敗，實際是同一筆

### 判定 checklist

把一筆 ERROR 計入事故根因前，至少打勾：

- [ ] 訊息內容真的是失敗語意（不是「ErrorMessage: OK」這種）
- [ ] severity 與內容一致（不是被工具誤標）
- [ ] 頻率與業務指標相關（不是長期都這樣的背景噪音）
- [ ] 來源是真實業務流量（不是 probe / bot / 內部測試）
- [ ] 不是同一個事件的多筆拆行 / 多次 retry

## 階段 5：跨來源關聯（這才是調查的精髓）

**單一來源不能下結論，必須交叉。**做法：

1. **找對照組**
   把「同時段在工作的東西」找出來。例如：
   - 同 LB 上的其他 endpoint
   - 同 Pod 的其他 endpoint
   - 同上游廠商的其他訊息類型
   - 前後一小時的同類流量

2. **追 trace / request id**
   能對到就用 trace 串起來；對不到就退一步用「時間戳 ± N 秒 + 業務 ID」做近似關聯。

3. **業務 ID 反查**
   訂單號 / 使用者 ID / session ID / 廠商單號 拿到全部來源去 grep。

4. **時間軸對齊（最有力的證據呈現方式）**
   把所有可疑事件按時間排成單一表：

   ```
   時間 (時區明示)         | 來源        | 觀察
   2026-05-03 01:37:29 +0800 | 業務 DB     | bet_at 寫入 #44790906
   2026-05-03 01:37:30 +0800 | LB log      | （此處應有 settlement callback，但不存在）
   2026-05-03 01:37:30 +0800 | 應用 log    | （此處應有 op=settlement INFO，但不存在）
   2026-05-04 00:00:10 +0800 | 業務 DB     | end_at 寫入 + manual_fetch=true
   ```

   時間軸表會直接讓「哪一步不見了」浮出來。

## 階段 6：根因判定 Checklist（要說「不是我們的問題」之前）

要做「**這是上游/廠商問題，不是我方問題**」這種斷言之前，至少打完以下勾：

- [ ] 同時段、**同條鏈路**的其他端點 / 其他訊息類型是正常的（→ 鏈路本身、TLS、DNS、LB、防火牆排除）
- [ ] 我方應用層該時段沒有 5xx、沒有 panic、沒有 OOM、沒有重啟、沒有 readiness 持續失敗
- [ ] 我方該時段沒有部署、沒有改設定、沒有改防火牆、沒有改 IAM
- [ ] 上游有資料但沒送達（用上游 query API 撈得到 → 證明對方有結果，只是 push 沒送）
- [ ] 影響範圍與「上游某模組壞了」吻合（例如只壞 settlement，不壞 betting → 對方 settlement 模組嫌疑大）；與「我方共用元件壞了」**不**吻合
- [ ] 排除掉內部人員手動操作的可能（例如有人用 Postman 在同時段戳那個 endpoint，這不算事故）

任何一格沒打勾，**不要說滿話**。寫成「目前證據傾向 X，但 Y 尚未排除，需要追加 Z 驗證」比較誠實，也讓使用者有空間決定下一步。

反過來：「**這是我方問題**」的判定也要對等嚴謹，不要為了「給個交代」自己背鍋。

## 階段 7：產出（給人看、給對方看、給未來看）

調查結束至少給出三份東西：

### 1. 時間軸總表
誰、什麼時間（含時區）、做了什麼、結果如何。

### 2. 根因判定 + 證據
- 結論一句話
- 支持證據條列（每條對應一個來源）
- 已驗證 vs 尚未排除明確區分
- 必要時用 checklist 形式呈現給使用者複核

### 3. 後續行動三類

| 對象 | 內容 |
|---|---|
| 我方營運 | 缺什麼資料要補？需要手動修哪些訂單 / 錢包 / 分潤 / 流水？ |
| 對方廠商 | 對方需要回答的具體問題（時間區間、單號清單、要對方提供的證據） |
| 系統面預防 | 補單頻率調整、補單 pipeline 完整化、新增告警、新增 reconciliation 機制 |

### 額外：對外溝通草稿
若需要發訊息給廠商 / 客戶 / 同事，提供草稿時要包含：
- 時間區間（**含時區，雙語事件可能要 UTC + 當地時間並列**）
- 影響範圍（域名 / endpoint / 受影響單號清單）
- **我方已驗證的事實**（讓對方知道你做完功課了，不是甩鍋）
- 要對方確認/回答的**具體問題**（編號條列，不要散文）
- 視對方語言準備中英對照

> 廠商信不寫死模板。每次根據事件性質、對方關係、緊急程度調整語氣。

## 反模式（自我察覺，看到自己在做就停）

1. **沒問時區就開查**
2. **看到一個 ERROR 就斷定是事故根因**（沒做雜訊辨識）
3. **只查一個來源就下結論**（沒做交叉）
4. **把全部日誌拉下來塞進 context**（沒分層假設、沒挑來源）
5. **對使用者說「沒問題」其實只查了一個來源 / 一個時段**
6. **默默執行 modify 動作**（例如 `kubectl scale 0 想看是不是會復活`、`重啟 Pod 看看好不好`）→ **絕對不行**
7. **直接複製貼上「上次的查詢指令」**（每次事故的時段、域名、資源名都不同，硬抄會錯）
8. **沒寫時區就交時間戳**（給使用者看的時間一律明示時區，給日誌系統的查詢一律用 UTC ISO 8601）
9. **下完結論才開始想下一步**（後續行動應該與調查同步思考，不是事後補）

## 啟動後的第一個動作（**必做順序**）

當本 Skill 被觸發，回應使用者前先依序：

1. **印出當前認證身份**：account / IAM principal / 專案 ID / 訂閱 ID / region，以及你判讀的權限等級（readonly / 高權限）
2. **明示唯讀承諾**：「本次調查維持 read-only，需要任何修改我會逐項詢問」
3. **回放使用者陳述 + 列缺漏**：把使用者目前說的事件條件複述一次，列出你還需要問的關鍵資訊（時區、影響範圍、上下游、定義）
4. **提出第一個假設 + 計畫驗哪個來源**：說清楚「我打算先驗 A 還是 D，用什麼來源、預期看到什麼才算驗證、看到什麼會打槍」，等使用者點頭再動手
5. **動手後每一步用「人話」敘述觀察**：不是貼整段日誌，是貼結論 + 必要的證據片段

## 多雲適用提醒

本 Skill 思路通用，但**操作細節差異要自己 cover**：

- **動詞名稱不同**：GCP `gcloud logging read` / AWS `aws logs filter-log-events` / 阿里 `aliyun log GetLogs`
- **時間格式不同**：RFC3339 vs ISO8601 vs Unix epoch ms
- **權限模型不同**：GCP service account impersonation / AWS assume role / 阿里 RAM
- **日誌延遲不同**：有些雲日誌延遲可達數十秒，太靠近現在的時段可能還沒進來
- **配額限制不同**：日誌查詢 / 指標查詢都有 rate limit，注意不要短時間內爆衝

不確定當前雲對應工具時，**先問使用者「你希望我用哪個 CLI / 工具？」**，不要靠猜亂打指令。

## 結語給下一個 AI

事故調查的價值不在「跑了多少查詢」，而在「下了什麼判斷」。多想、少查、明示假設、留下時間軸、誠實標記不確定範圍——這比 1000 行 grep 結果有用。

最重要：**永遠先確認你是不是只能看，不能動。**
